# I/O fix before Gaia DR4: DataLink data-structure rename (2026-11-22)

**What changed:** `io_gaia.py` 0.1 -> 0.2.0. This is a download-layer fix only. No model, statistic,
threshold, target, prior or verdict rule in any pre-registration changes.

**Why.** Release 3.15 of the Gaia ESA Archive (2026-10-14) renamed the DataLink data structures:

- `INDIVIDUAL` is now `DATAMODEL_STANDARD`;
- `RAW` is now `DATAMODEL_GAIA`.

Sources: Gaia news of 2026-10-14 (https://www.cosmos.esa.int/web/gaia/news) and the archive release
notes (https://www.cosmos.esa.int/web/gaia-users/archive/release-notes). astroquery's development
version changed its default to `DATAMODEL_STANDARD` in PR #3629. Our 0.1 code asked only for
`DATA_STRUCTURE=INDIVIDUAL`. The release notes do not say whether the old name is still accepted.

**What 0.2.0 does:**

1. It asks for `DATAMODEL_STANDARD` first, then `INDIVIDUAL`, then no `DATA_STRUCTURE` parameter at all.
   Each is tried with the `Gaia DR4 <id>` and bare-id forms, and in CSV and VOTable.
2. It keeps a downloaded file only if it parses into epoch-astrometry rows: at least one row, with a
   `centroid_pos_al` column. Before, any response longer than 200 bytes was stored as data. An archive
   error page would then crash the job after the download loop instead of moving on to the next URL.

**Checked:** `bright_source_epoch_astrometry` holds only 49 of the 51 brightest stars, and
`crowded_field_epoch_astrometry` holds only crowded-field sources. None of our targets is in either,
so `RETRIEVAL_TYPE=EPOCH_ASTROMETRY` stays right
(https://www.cosmos.esa.int/web/gaia/dr4, product table of 2026-09-14).

**Also noted:** the archive is offline from 2026-11-25 12:00 CET until DR4 opens on 2026-12-02 at
12:00 CET. Users may run at most 5 jobs in parallel. A live probe of the DataLink service
(`probe/` in gj3512-giants-dr4) is queued so that the behaviour of the old and new names is on
record before DR4.

Tests: `test_io_gaia.py` (standard library only, no network).
